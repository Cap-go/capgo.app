# Customer key custody for native builds and live updates

**Status:** Proposed architecture. A maker should be able to set up signing once, ask an assistant to build or publish, and see which app, artifact and destination they are authorizing. There are two distinct promises.

| Customer material | Who can use plaintext? | What the assistant receives |
| --- | --- | --- |
| Apple distribution identity, Android keystore and associated passwords or store credentials | Proposed isolated mode: credential intake and the authorized signing or publishing workload. Legacy mode: project-controlled Gradle and Xcode phases can also read credentials. | Setup link, credential status and build ID |
| Private key paired with the public key embedded in CapacitorUpdater | Customer-controlled software on an enrolled device or runner | Approval request, artifact digest and release status |

## Native builds

Today the [credential service](../supabase/functions/_backend/public/build/credentials.ts) accepts credentials, [seals them](../supabase/functions/_backend/utils/build_credentials_crypto.ts) with AES-GCM bound to app and platform, and can decrypt them for a build. Its secret can fall back to API_SECRET. The [hosted MCP](../supabase/functions/_backend/mcp/tools.ts) can already prepare a single-use upload URL and request a build with stored credentials. The [authorization check](../supabase/functions/_backend/public/build/stored_credentials_access.ts) requires app settings permission because build scripts can read signing secrets.

1. Add a signed-in setup page with file pickers and password fields. An assistant can open the page by app and platform. It contains no bearer credential in its URL. After confirming app, platform and merge or replace, the page obtains the existing short-lived upload capability and submits directly over TLS. Exclude analytics, session replay, request-body logging and third-party scripts from secret entry. Return the existing redacted status.
2. Give each credential version a random data key. Encrypt with authenticated org, immutable app identity, platform, purpose and version. Store ciphertext and a KMS-wrapped data key. Restrict wrap and unwrap to separate workload identities. Human support and general API workers can inspect status. An isolated signing service can unwrap only after validating a short-lived job grant against current authorization, credential version and artifact digest. Enforce one job per grant with atomic consumption and idempotent status lookup.
3. Run project-controlled build scripts before releasing credentials. Sign the completed artifact in a disposable workload with fixed tools, an isolated temporary keychain or keystore and restricted egress. Give store upload credentials only to the publishing step. Destroy temporary material on success, failure and timeout. Retain today's admin gate until each supported build mode demonstrates that customer hooks cannot access signing material. Keep legacy modes explicitly identified where they still expose credentials to scripts.
4. Migrate existing rows with bounded, restartable batches and conditional version updates. Verify a new envelope opens inside the signing boundary before retiring the old version. Keep the old reader during rollout and retire old decryption secrets after migration and the backup retention window. Record access, rotation, failure, and deletion using identifiers and outcomes only.

## OTA private keys

**Trust boundary.** Capgo stores an encrypted copy and coordinates operations. A normal API key is presented to Capgo, so deriving an unlock key from that bearer would let Capgo derive it too. A password reset, organization administrator action or hosted MCP call must never create a decryption recipient. The guarantee covers the hosted control plane, database, backups and build workers. It depends on the integrity of customer-controlled client software. A web page whose JavaScript Capgo can replace on each visit cannot independently enforce this boundary.

**Shell-free enrollment.** Ship an independently verifiable, version-pinned signing client with a file picker and OS-protected local storage. A maker opens it from the setup page, signs in, imports the existing private key or generates a new one, and verifies its public fingerprint against the project's trusted native configuration. Enrollment is optional. For an enrolled release, the publisher must require an encrypted artifact with a session key and customer-authenticated checksum. The installed updater must independently reject a missing session key, a missing or invalid checksum, and any plaintext fallback using the verification policy and public key shipped in its native binary. Qualify each supported updater version against these cases before offering this mode. Legacy plaintext releases carry no customer-authenticated publication guarantee.

The client generates a random 256-bit data key per private-key version and encrypts the private key locally with AES-256-GCM and a fresh 96-bit nonce. Use a reviewed HPKE implementation to wrap the data key for each enrolled recipient. Bind org, immutable app ID, purpose, format version, key fingerprint and key revision to both layers using canonical encoding. Store the encrypted envelope, recipient wraps and public metadata in an app-scoped record with compare-and-swap revisions. Each new recipient proves possession and an existing trusted client verifies its fingerprint out of band before creating a wrap. Authenticate the recipient manifest with a customer-held enrollment signing key pinned during setup. Clients retain their highest accepted revision and verify the trusted project fingerprint on restoration. Never enroll a key solely because the API listed it.

**Recovery.** During setup offer a separate randomly generated offline recovery recipient. Export its private recovery kit directly to the maker and verify a restore before showing backup as complete. Include the enrollment authority recovery material and trusted fingerprints in that kit. A second enrolled device or the kit can authorize replacement devices. Losing every recipient and the kit means losing access. A replacement OTA key then requires shipping a native release with its public key. Removing a recipient prevents future service access. Previously copied envelopes and keys remain usable, so suspected compromise requires actual OTA key replacement and a native rollout.

## Reusing the key

| Entry point | Proposed experience |
| --- | --- |
| Hosted MCP | Create a pending operation and open the signing client via a short-lived link. The link identifies the request. The client authenticates independently, displays the app, artifact digest, channel and action, and obtains approval. |
| Local MCP or CLI | Send the artifact and requested operation over authenticated local IPC to a separate, customer-approved signer. OS permissions reserve the recipient identity and signer memory for that process. The signer validates the digest, obtains approval, and returns only the encrypted artifact and release metadata. |
| Customer API integration or CI | Pair the runner once. Provision an app-scoped API token and a separate recipient identity in the customer's secret store. An SDK profile references the API token and the isolated runner signer. Only the signer can access the recipient identity. Bind unattended approval to allowed app, channel and trusted artifact source. |

For each release the signer verifies the intended artifact against a customer-trusted digest or build provenance, fetches the envelope, opens it locally, and runs the existing [bundle encryption and checksum flow](../cli/src/bundle/encrypt.ts). Upload only the normal updater-compatible outputs. Bind the approval to a nonce, expiry, key version, input digest and destination. Recheck authorization at publication, atomically consume the approval, and return the prior result on a retry with identical inputs. Expired, changed or replayed requests cannot publish another artifact. If every customer signer is offline, show a pending approval until expiry. Never fall back to server-side OTA decryption.

## Delivery and acceptance

Start with the native setup page over the existing API. Introduce KMS and isolated signing behind an opt-in per platform. Separately prototype OTA enrollment, recovery and a single shell-free MCP release before enabling unattended runners. Keep existing CLI, API and updater formats compatible. Disabling either pilot stops new operations while preserving access to existing customer backups under their original policy.

Before release, demonstrate a maker completing both flows without a terminal. Install an OTA bundle on supported updater versions and verify public-key compatibility. Exercise org transfer, revoked permissions, cross-app substitution, altered envelopes, injected recipients, duplicate approvals, concurrent rotation, offline signers and recovery on a clean device. Require reauthorization and client-side rewrapping on org transfer. Inspect service traffic, logs, traces, crash output, build archives and backups with synthetic canary keys. Verify that a database export plus all server-held API and KMS credentials cannot open the OTA fixture. For native signing, test each supported artifact type with a fixture build hook that checks whether signing credentials are visible. Gate rollout on those results and an independent review of the envelope and enrollment protocol.
