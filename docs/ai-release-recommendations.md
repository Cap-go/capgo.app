# AI release recommendations

Deploy the migration and backend before releasing the CLI. Deploy the companion admin dashboard change after the migration. The minimum supported CLI version stays unchanged. Existing `bundle upload --auto-bump ai` and published CLI RPC contracts are unchanged.

`POST /bundle/recommend` uses API-key middleware and `app.upload_bundle` permission. The application and history are read with the caller's RLS context. Paid entitlement is checked using the existing plan lookup plus live Stripe subscription status; trials, overdue and cancelled subscriptions are excluded. Administrative counter writes and name-occupancy checks run only after authorization, scoped to the resolved app and owner. No grants on existing RPCs change.

The provider is Workers AI with the existing AI binding. `RELEASE_RECOMMENDATION_MODEL` overrides the default. The live catalog on 2026-11-11 lists `@cf/deepseek-ai/deepseek-v4.1-flash-1017` as created 2026-10-17 with no planned deprecation. Its schema supports `reasoning_effort: none`, `chat_template_kwargs.enable_thinking: false`, and OpenAI-shaped JSON schema output. The live smoke call was rate-limited (HTTP 429); successful inference and disabled reasoning still need verification before release.

Requests are capped at 64 KiB, with per-field limits. Context contains summaries and file statistics only, not source diffs. Backend prompt history is limited to 30 versions and comments to 500 characters each. The new `(app_id, id DESC)` index makes history bounded by one app, avoiding a global scan of the large version table. Existing `(app_id, name)` indexing supports the name-occupancy check. No plugin request path changes.

Execution model: one permission check per request, followed by RLS reads of one app and at most 30 returned versions (RLS helpers may evaluate per candidate). No new SQL functions, policies, triggers, cron jobs, queues or extensions are added. The composite index keeps history candidates local to an app; existing schema indexes cover app and billing identities. This is an explicitly invoked CLI workflow, not millions-per-day plugin traffic. Check index creation duration against the production version table before applying the migration.

`ai_release_usage_daily` stores counters by UTC date, organization and app. The primary key begins with date for bounded admin trend queries. Counters increment atomically before inference. A database accounting failure prevents inference; there are no provider retries. Successful validated responses and failed attempts increment separate counters. Interrupted attempts remain visible as requests minus successes and failures. Changelog requests are a subset of total requests. No request bodies, provider errors, responses or changelog drafts are persisted. Counts survive app removal and remain attributed to the original owner after transfers; organization deletion cascades to its counts.

The admin dashboard remains in Cap-go/capgo_admin_dashboard. Its separate read-only Access-protected endpoint aggregates these counters over a bounded range and charts the daily trend. No admin code lives in Capgo.
