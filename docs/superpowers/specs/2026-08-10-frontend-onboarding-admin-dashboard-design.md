# Frontend Onboarding Admin Dashboard Design

## Goal

Add a read-only platform-admin page named **Frontend onboarding** that shows where new users leave the frontend app-creation wizard. The first version covers only the `pre_org` flow and measures progress until the user reaches the final setup screen containing the CLI command.

This page measures the early frontend experience. It does not measure whether the user later runs the CLI, publishes an app to a store, or successfully deploys an update.

## Scope

Version 1 includes:

- the existing shared admin date selector;
- an informational `Onboarding v1` badge;
- four KPI cards;
- one daily attempts column chart;
- one full-width tapered funnel;
- PostHog data read through the existing platform-admin backend endpoint.

Version 1 excludes:

- the `existing_org` onboarding flow;
- intent, organization, app, or version filters;
- demo-app analysis;
- session-replay or per-user tables;
- store-import analysis;
- CLI execution or later product-activation milestones;
- special PostHog configuration, connection, retry, or truncation UI.

## Page and Navigation

Add `Frontend onboarding` to the existing admin dashboard tabs and expose it at `/admin/dashboard/frontend-onboarding`. The page follows the same authorization, layout, shared date-range state, loading pattern, and `useAdminDashboardStore.fetchStats(...)` path as the existing admin dashboard pages.

The page contains, in order:

1. A header with `Frontend onboarding` and a fixed `Onboarding v1` badge.
2. Four KPI cards.
3. A `Daily onboarding attempts` chart.
4. A `Frontend onboarding funnel` chart with the stage conversion figures shown below it.

There is one funnel, not separate side-by-side funnels, because `existing_org` is deliberately deferred.

## Attempt and Cohort Semantics

An attempt is identified by the `onboarding_attempt_id` property generated by `createOnboardingProgressTracker`. A browser refresh remounts the tracker and creates a new attempt ID. Returning to onboarding later also creates a new attempt when a new tracker instance is mounted.

Only events matching all of these conditions participate:

- event name is `onboarding_step_viewed`;
- `flow = 'pre_org'`;
- `onboarding_version = 1`;
- `onboarding_attempt_id` is non-empty.

An attempt belongs to the selected reporting period when its first `intent` view is at or after the selected start timestamp and before the selected end timestamp. Events for that attempt may contribute to its progress for up to 24 hours after the first `intent` view. Events after that window are ignored. The preceding comparison cohort uses the half-open period immediately before the current one with the same duration, so the cohorts never overlap.

Repeated views of the same step are deduplicated by taking the first timestamp for that step. A later step implies that all earlier steps were reached, which keeps the funnel monotonic if an intermediate view event is missing.

The `resumed` property is retained in the source events but is neither a filter nor a separate segment in version 1.

## Funnel Definition

The funnel uses viewed events because the product question is whether the user successfully moved to the next visible screen. Its stages are:

1. **Intent** — the first `intent` view; this is 100% of the cohort.
2. **App details** — a `details`, `organization`, or `setup` view exists.
3. **Organization** — an `organization` or `setup` view exists.
4. **Setup reached** — a `setup` view exists.

`Setup reached` is the frontend completion milestone. The existing `onboarding_step_completed` event for `setup` is not used because it currently represents clicking the dashboard exploration action, not merely reaching the final setup screen.

Each funnel stage returns:

- the number of attempts that reached it;
- the percentage of the starting cohort;
- the drop-off percentage from the preceding stage.

The tapered chart uses the existing `AdminFunnelChart`. The figures below the chart make the exact stage-to-stage percentages readable without relying on tooltips.

## KPI Definitions

The four cards are:

1. **Onboarding attempts** — unique attempts whose first Intent view is in the selected period.
2. **Frontend onboarding completed** — primary value is the percentage of attempts that reached Setup within 24 hours; supporting text is the completed-attempt count.
3. **Median completion time** — median elapsed time from first Intent view to first Setup view among completed attempts only.
4. **Largest drop-off** — the highest relative loss between consecutive funnel stages, with the affected transition named in supporting text.

Each KPI may show a comparison with the immediately preceding period of equal duration. The comparison uses the same cohort and 24-hour completion rules. When a percentage comparison has no meaningful prior denominator, the comparison is omitted rather than displaying an infinite or misleading change.

## Daily Attempts Chart

The daily chart groups attempts by the UTC calendar date of their first Intent view, matching the ISO UTC boundaries sent by the admin store. It contains one series, `New user onboarding`, because version 1 covers only `pre_org`.

Reuse `AdminStackedBarChart` with a single dataset. Although the component supports stacked data, using it here avoids a second bar-chart implementation and leaves room for an additional onboarding source later without changing the page structure.

## Backend and PostHog Reuse

The frontend requests a new `frontend_onboarding_analytics` metric category through the existing `POST /private/admin_stats` endpoint and `useAdminDashboardStore.fetchStats(...)` store method. The existing five-minute store cache and selected date range apply unchanged.

The existing Builder Analytics utility already contains the generic PostHog read behavior: backend-only credentials, HogQL request construction, timeout, response-to-row mapping, and logging. That transport should live in a shared backend utility and be used by both Builder Analytics and Frontend Onboarding Analytics. If the implementation base already contains the extracted `queryPosthogHogql` helper, reuse it directly; otherwise extract only that generic transport from `builder_analytics.ts`. Do not duplicate the PostHog HTTP client and do not expose its credentials to the frontend.

Create a focused onboarding analytics helper that owns only:

- the fixed version-1 HogQL query;
- conversion of PostHog rows into attempt summaries;
- current- and previous-period aggregation;
- KPI, daily-series, and funnel response construction.

The HogQL query should return one row per attempt with its cohort start and first timestamps for the four relevant steps. It must query enough time to cover the previous cohort and both cohorts' 24-hour follow-up windows.

The response uses the repository's existing snake-case analytics style:

```ts
interface FrontendOnboardingAnalytics {
  onboarding_version: 1
  kpis: {
    attempts: number
    completed: number
    completion_rate: number
    median_completion_ms: number | null
    largest_dropoff: {
      from: 'intent' | 'details' | 'organization'
      to: 'details' | 'organization' | 'setup'
      percentage: number
    } | null
    comparison: {
      attempts_percent: number | null
      completion_rate_points: number | null
      median_completion_ms: number | null
      largest_dropoff_points: number | null
    }
  }
  daily_attempts: Array<{ date: string, attempts: number }>
  funnel: Array<{
    key: 'intent' | 'details' | 'organization' | 'setup'
    label: string
    reached: number
    of_start_percent: number
    dropoff_percent: number
  }>
  posthog_configured: boolean
  posthog_connected: boolean
}
```

The connection fields remain in the network response for diagnostics and consistency with existing analytics code, but the new page does not render dedicated warning banners for them. Existing backend logging and the normal frontend `try`/`catch` console logging are sufficient for this internal page.

## Versioning

Version 1 is fixed in both the query and page badge. There is no generic version selector because an onboarding version can change the number or meaning of stages.

When version 2 is introduced, it must define its own funnel configuration and labels. A future version tab or selector will switch the entire configured query and funnel definition rather than mixing versioned events into one tunnel.

## Empty and Loading Behavior

Use the existing component loading states while `fetchStats('frontend_onboarding_analytics')` is in flight. A successful query with no attempts naturally renders zero-valued KPI cards and empty charts. A request error follows the existing admin-page pattern: log it and leave the page without data. No new retry control or PostHog-specific warning banner is added.

## Testing

Backend unit tests cover the onboarding-specific aggregation independently from the network transport:

- filters to version 1, `pre_org`, viewed events, and non-empty attempt IDs;
- assigns attempts to cohorts using first Intent time;
- deduplicates repeated step views;
- infers earlier stages from later views;
- excludes progress more than 24 hours after Intent;
- computes daily attempts, completion rate, median duration, and largest drop-off;
- computes the immediately preceding equal-length comparison period;
- handles zero attempts and missing prior-period denominators.

The shared PostHog transport retains or gains focused tests for missing credentials, successful row mapping, non-2xx responses, timeouts, and malformed responses. Existing Builder Analytics behavior must remain unchanged after extraction.

Endpoint tests verify that `frontend_onboarding_analytics` is accepted by the admin-stats schema and dispatched to the new helper. Frontend tests verify the new tab, request category, fixed version label, and transformation of the response into the four cards and the two existing chart components. No new chart implementation test is needed.

## Success Criteria

The feature is complete when a platform admin can select a date range and see, for onboarding version 1 and the `pre_org` flow, the number of attempts per day, the four approved KPIs, and a monotonic Intent-to-Setup funnel derived from unique `onboarding_attempt_id` values. The implementation must reuse the existing admin-stats route, dashboard store, PostHog backend transport, and shared chart components without adding customer-facing analytics behavior or admin mutation capabilities.
